## Phase 1: intake identity verification: IN PROGRESS (see commits below)
Done:
- Migration `20261126090000_pending_registration` (new model `PendingRegistration`, enum `PendingRegistrationStatus`). Additive, no backfill, no FKs.
- `pending-registration.{repo,service}.ts`: anonymous `POST /intake/register` creates ONLY a pending row (202); `POST /intake/register/verify` atomically claims the row and creates User(emailVerified) + Applicant(PENDING) + StudentProfile(ACTIVE) in one transaction, then issues the session; `POST /intake/register/resend` (cooldown 60s, max 4 sends, optimistic rotate).
- Code stored as `hashOTP(`${pendingId}:${code}`)`; compared with `timingSafeEqual`; attempts counted before comparison (5/code, committed independently); 5 submissions/email/hour; per-IP limiters on all three routes.
- Signed-in verified user + matching email: finalized immediately. Unverified session: 403. Existing account/applicant for the email: 409 (never silently linked).
- New email job `application-verification` (+ template `src/views/applicationVerification.ejs`).
- Cleanup cron rewritten: only deletes abandoned unverified users that own nothing; jobs isolated with `Promise.allSettled`; sweeps pending registrations (expire, scrub PII, purge after 7 days). Previously one unverified user with a StudentProfile made the delete throw (FK Restrict) and the other jobs were lost.
- Seat checkout now requires `emailVerified` (`EMAIL_VERIFICATION_REQUIRED`).
- Legacy credential recovery: when a legacy unverified account that holds a StudentProfile verifies via `/auth/verify-email`, its credentials password is cleared (the password may have been chosen by someone else); the owner sets one through forgot-password.
